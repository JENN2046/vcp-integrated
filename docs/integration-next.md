## 推荐施工顺序

1. **收敛 B 末代终稿补交。** 只针对支持原生终稿发布的 ToolBox 和显式工具单聊 B 末代。新版桌面凭 Work、代次、回复 ID 和中央发布序号读回，再经原队列投影。能力未知／老服务端继续走兼容补交。先核对当前接口能否可靠表明这份终稿已提交；单个 `model_terminal` 标志不足以切路。以现有三次丢终态与已发布丢 ACK 为对照，额外记录正常收包时新版 B 产生的补交 POST 数。验收为新组合零冗余补交，唯一 Journal、History 和正式气泡；编辑与墓碑保持，原工具一次；旧桌面精确回执仍可重放。无法确认时保留原身份待核对。[终稿基线](evidence/native-final-publication/desktop/README.md) · [编辑、删除及旧版回执](evidence/shared-single-review/final.json)
2. **形成一个三端隔离候选。** 固定第 1 批提交，在干净检出按锁定输入重建，记录实际加载的桌面、ToolBox、PWA 与原生资产哈希。Linux 跑普通本机与共享发送；原 Windows 虚拟机重开同一话题，核对 ID 与正文；Android 用系统文件选择器选择一个合成文件，补验明确拒绝、冷开改发、丢回执找回原 Work。另用一次性配对单测首次配对立即强停的会话保留情况。用旧合成库核对升级和回退边界，记录能保留哪些事实。交付可复建命令、已知限制及三端回执；日用安装和生产部署由 Jenn 另行决定。[既有三端证据](evidence/windows-device/README.md) · [Android 已验范围](evidence/android-send/phone/README.md)
3. **复测空闲成本，再选一处减法。** 同一候选用两个已追平的桌面和一个后端，复用原测量窗口、进程范围与口径，分别记请求种类、逻辑读取、持久写入、CPU。锁定一个可归因的重复操作再改；用断线、重开、游标追平和真正产生的新消息证明无漏投。若当前成本已无有意义的热点，就以测量结果收尾。
4. **整理规则和配置入口。** 分两次选题。规则侧优先核对仍有源码实现的请求封装／元数据入口，拿同一输入比对实际 handler 和 Provider。数据侧从一次原生保存或删除动作追到最终写入者，覆盖本机、共享、冲突草稿及丢回执。每批只消除一处实证重复，保留必要的协议校验和恢复凭据。

扩展多工具、AA、群聊接力或完整 wire 1.6 兼容，等具体产品需求决定先后。多工具先验证多个 invocation 各自结算及未知副作用；AA 先定义父 Work 和子任务都能交出的安全边界；群聊先定义成员计划、已发布成员回复和剩余发言的归属。这些能力不能由单工具接续的通过结果推定。
