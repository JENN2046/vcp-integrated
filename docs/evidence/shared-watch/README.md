# 共享桌面静默同步验收

本轮实现 `shared-watch-v1`。两端保留同一物理 History 写入队列、原 Journal 游标和恢复账本。空间 SSE 提示有变化后才拉取；本机提交、附件到期和未完工作可独立唤醒。首次订阅、断线重连和分设备错开的 15 分钟审计负责补偿。兼容旧服务端的客户端继续走原 wait 路径。[协议与兼容边界](protocol.md)

## 空闲开销

12 组各运行 31 个完整分钟，合计 372 分钟。以下按两台 Electron 主进程及 ToolBox 的 NativeSync 归因汇总；CPU 单位为每分钟消耗的核秒。大夹具含 123 个 History 和 1,564 个 Journal 修订。其正文体量和旧现场不同，应使用同夹具的基线进行比较。

| 大健康夹具，每分钟 | 原代码，31 分钟均值 | 候选，连续健康 10 分钟 | 候选，含两次审计的 31 分钟均值 |
|---|---:|---:|---:|
| 新同步 HTTP 请求 | 33.68 | 0 | 0.52 |
| 可归因逻辑文件读取（MiB） | 0.9855 | 0 | 0.0168 |
| 可归因 CPU（核秒） | 1.500 | 0.0087 | 0.0368 |

健康小、大两组 10 分钟内均无同步文件写入，两条空间连接合计 80 个保活注释、1,040 个逻辑字节。短时 SQL 专测中，每次保活分别读取 source_bindings、native_sync_metadata、shared_members、ns_wait_versions 各一次，未访问 messages 或 Journal，未写入。大健康组每次审计由每端重新读 123 份 History，共 92,755 B。独立、无 JS 计量器的三进程 CPU 减去同规模关闭同步组，折合大健康组约 0.128 核秒/分钟（前 10 分钟）、0.209 核秒/分钟（全 31 分钟）。这是同宿主底噪差值，有调度波动；0.10 的目标按 NativeSync 归因计量通过。

已有缺件时，31 分钟产生 16 次审计请求和 14 次到期 404；另一个正向场景上传后约 52 秒两端恢复附件，未新增模型调用或 Journal 记录。单独打开已追平话题的两分钟窗口仅有空间和话题 SSE 保活，无新业务请求。[复现命令与计量口径](idle-method.md) · [完整汇总、加载哈希与底噪](idle-receipt.json) · [逐分钟记录](idle-windows.jsonl)

## 投递、权限和终端可见性

后台观察端对齐耗时 205 ms。提交发生在订阅建立前、发生在首轮拉取尚未完成时、仅切断 watch 而保留业务 HTTP，均能按序追平。6 次发送对应 6 次模型调用、12 条唯一消息。真实权限变更使在途订阅关闭；同一 Profile 随服务端重启恢复。配置响应在传输过程中和本地异步处理结束、交付窗口前，均核对发起时的授权。[故障回执](fault-receipt.json) · [测试方法](fault-method.md)

低负载回环样本在同一个前台话题中测量。中央提交到第二个有效动画帧，新回复 264–269 ms，编辑 79–84 ms，删除 74–79 ms。高负载对照中，新回复和删除超过 1 秒，因此 1 秒结论限于低负载样本。编辑和删除由已认证的 ToolBox 接口写入；桌面菜单编辑在提交前返回 SHARED_NATIVE_ADMISSION_REQUIRED，记录为原有写入入口的限制。[逐项时延、可见帧与环境](visibility-receipt.json)
