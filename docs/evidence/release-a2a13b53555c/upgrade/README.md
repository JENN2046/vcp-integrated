# 旧 Work 的升级与可恢复位置

使用本轮三端合成环境的冷种子：Linux 和 Windows 具有各自绑定，手机已建立一条只读会话，两个本轮业务话题为空。停服务后复制种子，在隔离副本中实际加载旧版 `af17c99e784f` 的存储、共享接力与原生请求模块，创建另一话题的 v1 双人成员计划。甲的正式回复在旧版本提交，Work 进入等待接管。此阶段与恢复阶段均通过宿主原生注册、模型终态和发布接口供应确定性合成结果，没有访问在线模型。

**备份点**为 Work `request_64d57d14472a40408307e77890f1d894`，schema 3，Journal 已有原输入（序号 1）和甲（序号 2）。SQLite backup 独立保存了这个位置。冷备文件 SHA-256、消息 ID、内容哈希、执行者、原生请求与原操作回执的哈希见[升级前后回执](upgrade.json)。

新版 `a2a13b53555c` 从备份副本冷开，逐项比对上述事实。设备 B 继续旧 v1 Work 后新增乙回复（序号 3），重复 finish 读回原回执。三端中央随后从这份已续完的数据库副本启动，同地址、同组绑定、同一手机只读会话。在另一群启用 v2 前，旧 Work 保持 completed。整批三端操作后再次比较旧话题的持久记录。

**回退演练**从运行中的三端中央做独立一致性备份。在另一副本上，旧宿主以 `SHARED_SCHEMA_UPGRADE_REQUIRED` 拒绝打开 schema 4，升级分支上的旧 Work 保持原样。重新取启用 v2 前的 schema 3 备份，用旧宿主冷开，确实回到“甲已确认，乙未执行”的同一 Work；按旧协议继续并完成，原消息和回复身份保持一致。恢复点之后的新 v2 Work 与普通单聊进度仍属于新版分支。两条分支、原备份相互独立。[旧宿主实际拒绝与恢复](rollback.json)
