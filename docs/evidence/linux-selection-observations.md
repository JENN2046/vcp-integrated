# Linux 共享回复完成时的文本选区观察

实体联验在 Linux 显示上运行隔离 Electron Profile，同一 Work 的 Android 结果另行记录。初次选区使用脚本设置 DOM Range，当时输入框已有独立草稿。原用户文本在运行阶段处于选中状态。终态出现后，同一话题的草稿、原用户消息 ID、新回复 ID 和对应 Journal 序号均正确，文本选区读回为空。滚动位置由 52 变为 0，终态视口和内容同为 704 像素，已无滚动空间。这次结果不能证明可滚动长历史的阅读位置保持。

| 独立复核 | 观察 |
| --- | --- |
| 短窗，真实 Electron，运行卡稳定后通过 Chromium pointer 拖选 | 一秒持有后放行 Provider，用户消息选区偏移始终为 [1,43]。观察到五次终态 DOM 变动，原选区文本节点和用户气泡始终连接。 |
| 60 秒持有，真实 Electron 和 CDS，真实 pointer 拖选 | 放行后保持同一文本、偏移 [1,43]、同一文本节点和气泡。在途与完成均通过真实 ToolBox 投影。 |
| 98 秒尝试 | 隔离进程提前收到 SIGTERM，没有终态结果。 |
| 初期拖选试跑 | 一次指针起点落在晚出现的运行卡，未取得有效的原用户消息选区。改为等待运行卡稳定并核对每个端点的命中元素后再重试。 |

静态核对显示，正常的共享历史刷新经 nativeHistoryRefresh 进入 chatManager.syncHistoryFromFile，优先追加新消息或更新确有变化的消息。它没有直接调用整段聊天清空。确有内容变化时，messageRenderer.updateMessageContent 会替换该气泡正文节点。全量重载经 loadChatHistory 清除现有聊天 DOM。两次取得有效 pointer 选区的复核均未看到旧消息节点被替换。首次实体联验发生的选区丢失保留为观察结果，直接原因尚未证实，本轮产品渲染源码保持原样。

下一轮若再次复现，先同时记录真实指针选区、焦点转移和原文本节点的连接情况。确认某处替换旧正文后，仅在同一话题、同一消息、相同选中文本仍可对齐且用户未主动改变选区时，考虑在该渲染边界按文本偏移恢复。
