# 共享 History 文件身份与压缩提交重试

原故障发生在桌面 A 核对本机 History 时。中央已经提交意图 `compact_eb14f9e7d0a69e11f4ea0d483166f102147a2182`，检查点位于 Journal 序号 9，A 的物理 History 也已有同一 ID。随后 A 的提交 IPC 返回 `HISTORY_IDENTITY_CHANGED`。旧宿主对同一条消息再次点击「压缩前文」，实测会重新准备并调用摘要模型。[原故障与重试对照](desktop/baseline.json)

## 文件和写入者

目标文件是原隔离 Profile A 的 `UserData/ns_eacc962a8dfc681fb4f70cd7/topics/ns_d0ea333d16dc4d659817258b/history.json`。原记录包含错误码、文件更新时序和事后文件状态。发生错误时的两次 stat 和写栈来自独立的 Electron 复现。复现中读写的是同一话题的本机 History，写入者是 A 的 NativeSync 共享事件投影：它重放已接收的检查点事件，沿原生话题写队列通过 `durableJson` 原子换名。即使消息内容不变，换名也会更换 inode。[文件路径、写栈与时间线](identity.md) · [逐步 stat 与 rename 回执](writer-trace.json)

## 中央成功、本机未确认

桌面将待确认状态与原有的压缩提交意图一起持久化。重试按原 ID、话题映射、中央提交回执及物理检查点的正文与元数据核对，确认后向界面交付同一检查点。后台投影即使先完成，仍可完成界面确认。旧版 A 留下的「准备已取消、提交已完成」记录，通过原话题的最新中央水位与原提交序号进行一次性识别。原故障资产的组件复核读回了序号 9 的同一检查点，篡改、删行和错话题均未被当作成功。[原 A 账本升级回执](original-retry.json)

用同一个右键菜单和本地合成 Provider 做了另一组端到端对照。为让修复后的拒绝路径也可测试，夹具在中央成功后、A 本地确认前执行一次队列外同字节换名。旧版重试后产生两个压缩意图、两次摘要、两条检查点；候选在第一次读取时同样拒绝，重试恢复原意图，摘要和检查点均为一个，重试前后 Journal 一致。A 退出后，B 用自己的原 Profile 重开。实际 handler、Provider 首轮和工具续轮均只收到一个原检查点，已压缩旧文为零；丢回执后找回同一 Work，工具只执行一次。[双端回执与复跑命令](desktop/README.md) · [候选请求](desktop/candidate.json)

回归结果：原生套件通过 237 项，6 项需要指定原故障资产，在独立运行的原账本专项中全部通过（该专项共 13/13）。协作套件 53/53，桌面压缩、文件身份与 History 生命周期相关测试 117/117。无故障的同端 `compact-e2e` 及跨端 `compact-cross-device` 均通过。
