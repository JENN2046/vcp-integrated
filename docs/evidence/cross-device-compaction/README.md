# 共享单聊压缩后的跨端发送

A 在原生桌面菜单中生成共享检查点后正常退出。B 用自己的设备身份和原 Profile 重开同一话题，看到 A 发布的检查点，再点击发送。测试期间，只有隔离 ToolBox 和回环合成 Provider 执行请求。

## 为什么需要改动

原 worker 先按消息的显示时间排列 History，再调用 VCPChat 的原生检查点选择函数。真实桌面对照中，一条已经进入 A 压缩输入的用户消息，其显示时间比检查点晚五分钟。在基线 `63b2fe70da9e` 上，B 的 handler、Provider 首轮和工具结果续轮都又收到了这条正文。丢回执后的身份恢复在基线上已能找回原 Work。

共享消息的位置现在取自该 ID 首次进入 Journal 的序号，内容取与本次请求水位相符的版本。显示时间仍保留在消息上。原生窗口选择函数负责取最新有效检查点，桌面从 Journal 投影完整 History。服务端沿用原 Work 的接纳、派发和恢复入口。[宿主差异](host.patch)

## 怎样核对

| 要核对的事实 | 观测点 |
| --- | --- |
| B 使用 A 的原检查点 | 比对 A 的提交回执、Journal、B 物理 History、原生窗口选中的消息 ID，以及实际 handler 和 Provider 正文。 |
| 已压缩正文不回流 | 对照 A 摘要请求中的来源正文，检查 B 首轮和工具续轮的完整请求，包括那条显示时间超前的消息。 |
| 丢回执后找回原 Work | 代理收到服务端成功的接纳响应后断开 B 的连接。检查 B 的未确认本地意图，随后重开 B 并按原请求 ID 查询，与接纳响应中的 Work ID 核对。 |
| 模型与工具不重跑 | 单列 B 的首轮请求、工具接收方记录和带工具结果的续轮。核对恢复前后的模型调用、工具计数、Work 尝试次数及 Journal 中的输入与回复。 |

两台桌面为同一 Linux 主机上独立的沙箱 Electron 进程，设备 ID、Profile、History 和持久请求记录各自独立。[桌面回执与截图](desktop/README.md)

## B 重开时的 History

单独修复了一个桌面时序问题。B 在启动期间读取共享 History，偶尔正碰上宿主切换 History 写入权限。一次实测中磁盘已有检查点，界面等了 30 秒也没有显示；另一次已显示正式回复，界面仍报 `HISTORY_AUTHORITY_PENDING`。共享快照的只读 IPC 现在等待正在进行的权限切换结束，再通过原入口核对投影和读取权限。权限切换失败或应用正在关闭时，读取仍会失败。最终两轮都在 B 重开后直接核对了检查点、B 输入和正式回复的 DOM ID。[改前读失败回执](desktop-history-read.json) · [改后恢复画面](desktop/B-recovered-original-work.png)

服务端另用两个有时差的检查点和一次旧消息编辑做了对照。基线选中了较早发布的摘要；候选按发布顺序选中最后一个，编辑过的旧 ID 也留在已压缩范围内。新输入即使显示时间较早，仍能连同检查点后的正式回复进入后续请求。[基线请求](pair/server-clock-baseline.json) · [候选请求](pair/server-clock-candidate.json) · [回归用例](../../../tests/native/shared-session.test.cjs)
