# 共享单聊压缩输入修复

**共享压缩按原消息 ID 选取 Journal 的最新版本。** 首次写入的序号决定顺序，最新序号决定正文和删除状态。已发布的助手回复沿用其原 ID。原生归档仍可验证执行证据，压缩器只从中补入有独立调用 ID 和结算凭证的工具结果。[宿主差异](host.patch)

| 同一组真实 ToolBox 操作 | 基线 `96b1114d47e2` | 修复后 |
|---|---|---|
| 编辑一条已有原生归档的助手回复 | 压缩输入有新正文，同时又出现一条旧正文 | 只有原 ID 上的最新正文 |
| 删除这条回复 | Journal 已写入墓碑，旧正文仍以合成 ID 出现一次 | 该回复在压缩输入中出现零次 |
| 两个不同回复 ID 写入相同正文 | 两条正式消息都在 | 两条都在。只编辑第一条，第二条保持原 ID 和正文；再删除第一条，只剩第二条 |

两组使用相同的合成输入、步骤和 Provider；ID、版本、墓碑序号和归档证明分别核对。发起准备后如果来源变化，会拒绝发布旧摘要；旧版按正文拼接而准备的原生证据输入也须重新准备。[改前回执](pair/baseline.json) · [改后回执](pair/candidate.json) · [并发与旧凭证回归](https://github.com/JENN2046/vcp-integrated/blob/032ad5fc27536c323eb5bd075e43282b9badf50e/tests/native/shared-compaction-input.test.cjs)

## 压缩、重开与下一次发送

在隔离 Electron 的原生菜单点击一次「压缩前文」。同机合成 Provider 实际收到五条来源消息，包括原 ID 的编辑后正文和不同 ID 的两条同文记录；两份已被修改或删除的原生助手旧正文均未进入摘要请求。ToolBox 将唯一检查点追加到 Journal 序号 **9**。原有八条 Journal 和五条有效物理 History 逐字段核对通过。

正常关闭并重开同一 Profile 后，检查点 ID 和哈希一致。首次发送的实际 handler 与 Provider 请求都包含系统提示、**一个检查点和本次输入**；再次发送时，检查点之后多出的内容正好是上一轮输入与回复以及本次输入。两次发送分别对应一个 Work、一次派发。验收只在同一桌面设备完成。[桌面链路回执](desktop/receipt.json) · [重开截图](desktop/checkpoint-reopened.png) · [复跑方法](desktop/README.md)
